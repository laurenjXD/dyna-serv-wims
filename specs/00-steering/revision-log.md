## `08` pick-list generation blocked for provisional item codes (2026-08-07)

Follow-up to the same day's "Master Inventory dynamic item-code pre-PO gap" entry below. The Product Owner asked whether DSGC/item-code resolution needs to be guaranteed before pick-list generation, given that a Trading (or Supplies) item can sit in Master Inventory with `dsgc_item_number IS NULL` — `item_code_is_provisional = true` — for a period after enrollment, before any Purchase Order exists.

Checked `08-outgoing-withdrawal-and-two-stage-commitment` against that read model and confirmed a real gap: R1.2 validated active item references, party/flow scope, UOM, quantity, and document metadata, but never checked `item_code_is_provisional`. Because `01`'s `displayed_item_code` always falls back to the internal `items.code` rather than ever returning null, nothing stopped a provisional/fallback code from being picked, and `pick_list_items.item_code` is written once as a permanent snapshot at Stage 1 commitment — never recomputed later — so a provisional code picked at generation time would be baked permanently into a priced, customer-facing `pick_list` and, downstream, `acknowledgement_receipt`, with no way to correct it afterward.

Resolved by adding a generation-time gate rather than a schema change: pick-list generation now validates `item_code_is_provisional` (per `01`'s `master_inventory_tracking` read model) for every requested line and refuses to generate or reserve any pick list containing a blocked line, returning a recoverable, item-naming validation error instead of partially generating the pick list. The check runs as an added step in the Stage 1 commitment transaction, immediately before the `pick_list`/`pick_list_items` snapshot is written, since that snapshot is the last point at which a provisional code could still be corrected instead of becoming permanent.

## Master Inventory dynamic item-code pre-PO gap and Movement History reference field (2026-08-07)

Follow-up to the same day's Master Inventory UI Pattern work (see the "Master Inventory / Inventory Register — table-with-expandable-rows UI pattern" and general landing page entries above). Resolved by resolving the displayed code at read time in the `master_inventory_tracking` read model rather than adding a column or a backfill job: `displayed_item_code` falls back to the internal `items.code` when the flow-specific code (`supplier_item_code` for VMI, `dsgc_item_number` for Trading/Supplies) is null, and a companion `item_code_is_provisional` flag records whether that fallback is in effect. VMI's fallback branch is defensive only, since `supplier_item_code` is populated at receiving and should not normally be null. The write path that eventually assigns `dsgc_item_number` remains an open item, flagged for whichever future spec ends up owning Trading purchase orders.

Separately, the expanded row's Movement History gains a per-transaction "Reference" field: `inventory_transactions.commercial_invoice_no` for incoming movements, `inventory_transactions.ar_reference_no` for outgoing Dispatch/Withdrawal movements. ## `02` RBAC/RLS design review — one blocking security gap, several underspecified mechanisms (2026-08-05)

Ran `rbac-rls-reviewer` against `02`'s design.md (no code exists yet; this is a pre-implementation document review). The three-layer UI/server/RLS enforcement posture and most §7.4 patterns (`wrr_documents`, `pick_lists`, parent-inheriting `wrr_items`/`pick_list_items`) were assessed as sound and genuinely enforced-at-data-layer in intent, not just assumed. Six findings needed fixing, all now resolved in design.md:

1. **Blocking security gap**: §3.2 stated null-`flow_type` party scope means "all externally applicable flows," excluding Supplies — but §7.2's `has_party_scope` helper was described as "honoring null as all allowed flows" with no mechanism actually excluding `'supplies'`, and no capability-model rule stopped Supplies resources from being modeled as `assigned_party`-scoped in the first place. A party user with a null-`flow_type` scope on a party that is also a Supplies vendor could pass `has_party_scope(vendor_party_id, 'supplies')` and read internal Supplies data — directly violating requirements.md FR-4.2 and acceptance criterion #7. This was intent-only prose with no enforced mechanism, the exact failure class this review exists to catch. **Fixed** with two independent, redundant gates: `has_party_scope`'s own match logic now explicitly excludes `'supplies'` from null-match; `can_access_party_resource` independently hard-denies any `assigned_party`-scope check where the target row's `flow_type = 'supplies'`, regardless of what `has_party_scope` alone returns. The capability catalog rule is now explicit: Supplies-flow capabilities MUST be `scope_kind = 'global'`, never `assigned_party`.
2. **`lots`/`inventory_transactions` had one uniform `owner_party_id`-based RLS pattern**, but `owner_party_id` is required-and-authoritative for VMI while optional-and-not-the-customer for Trading (the warehouse owns Trading stock pre-sale; the same lot can split across multiple customer pick lists). A uniform policy would either wrongly deny Trading customers their own picked lot or leak an unrelated party's lot. **Fixed**: explicit two-branch policy — VMI uses `owner_party_id`; Trading joins through `pick_list_items.lot_id` → `pick_lists.customer_party_id`; Supplies is never party-scoped (per finding 1's rule). `inventory_transactions` inherits the same branch since it has no direct party column.
3. **`items` party-visibility had no join path specified at all** (unlike every other §7.4 row, which names exact columns). **Fixed**: party-user item visibility is now defined as derived only through `item_id` values reachable via the caller's own scoped `wrr_items`/`pick_list_items` records, excluding `default_supplier_party_id`/pricing fields from that projection — never a direct catalog read, and `default_supplier_party_id` is explicitly barred from ever being used as an RLS predicate (it identifies the warehouse's supplier, not the requesting party).
4. **`SECURITY DEFINER` helper owner/grant strategy was underspecified** — unclear how the helpers read RLS-protected `role_permissions`/`user_party_scopes` without either breaking (too-narrow grants) or over-granting (bypassing everything). **Fixed**: named a dedicated `rbac_definer` owner role with `BYPASSRLS` and table-scoped `SELECT` only on the specific tables these four functions read; ordinary roles get `EXECUTE` on the functions, never direct table access. Also fixed: these helpers must never be exposed as client-callable Supabase RPC endpoints (boolean-oracle enumeration risk) — added an explicit no-RPC-exposure requirement and a real-Postgres test for it.
5. **Last-administrator invariant lock (§8.5) was imprecise enough to permit a still-racy "spec-compliant" implementation**: a per-row lock on only the target administrator being revoked does not serialize against the aggregate count — two concurrent revocations of two *different* administrators can each independently see "1 will remain" and both commit, leaving zero. **Fixed**: specified a single fixed-key `pg_advisory_xact_lock` on a constant identifying the invariant itself, serializing all such operations globally. Also fixed: §8.3 (role revocation) didn't reference the invariant at all, even though FR-7.6 requires it for revocation as well as deactivation, and revoking the `administrator` role is a distinct code path from deactivating the profile — added the missing cross-reference.
6. Minor: §8's admin operations now state explicitly that privileged server functions must independently re-verify the caller's capability rather than trusting an upstream `requirePermission()` call; §6.3's transaction wrapper now states rollback must be guaranteed via try/finally on callback exception.

## `02` real-Postgres verification — 4 implementation-detail bugs found and fixed (2026-08-05)

Ran `db-migration-verifier` against `02`'s design with real disposable Postgres 16, hand-building stand-in `01` tables since no actual migrations exist yet. Six items requested, all PASS — but 4 real bugs surfaced only by actually running the DDL and invoking the functions, not by reading them, matching the class of bug this project has already been burned by (CBM/unit mismatches, library-version pins):

1. §4.6's `COALESCE(flow_type::text, '__sentinel__')` partial-unique-index approach fails outright — the implicit enum→text cast is `STABLE`, not `IMMUTABLE`, and Postgres rejects non-immutable expressions in an index. **Fixed**: switched to Postgres 15+'s native `NULLS NOT DISTINCT` index modifier, which is both correct and simpler than the original approach.
2. The four `SECURITY DEFINER` helpers all call `auth.uid()`, but `rbac_definer` had no grant to execute it — every call would fail with `permission denied for schema auth`.
3. `can_access_party_resource` calls other `rbac_internal`-qualified functions internally, but `rbac_definer` had no `USAGE` on that schema — `permission denied for schema rbac_internal`.
4. The admin mutation functions (owned by `rbac_admin_ops`, per §8's defense-in-depth re-verification requirement) call `rbac_internal.has_permission` internally, but had no `EXECUTE` grant on it — this broke the **entire admin mutation path**, caught on the very first concurrency test run, not an edge case.

All three grant gaps (2-4) are now folded into §7.2's owner/privilege strategy as explicit required grants, not left as implementation-time discoveries. The concurrency and Supplies-leak scenarios themselves — the actual security properties, as opposed to these DDL/grant mechanics — verified PASS with real concurrent Postgres backends and real row-level SELECT evidence, including a control experiment that reproduced the exact last-administrator race §8.5 exists to prevent when using only the row-level lock the design calls insufficient.

**Separately, real-Postgres review surfaced a genuine design contradiction** in the `items`/`party_visible_items` masking view (§7.4, from an earlier fix round): specifying it as a `security_invoker` view was backwards. A `security_invoker` view is subject to the base table's own RLS on top of its own filter — since party users correctly have zero direct grant on `items`, a `security_invoker` view would always return zero rows, defeating its purpose; loosening `items`' RLS to fix that would let a direct query on a now-visible row leak the very columns the view exists to hide. **Fixed**: the view must be a default (non-`security_invoker`) view owned by the same privileged role as the RBAC helpers, with the party-scope filter embedded in the view's own `WHERE` clause — Postgres evaluates a plain view's table access under the *owner's* privileges, not the querying session's, which is exactly the property needed here.

`02`'s Sign-off now has requirements/design review, `rbac-rls-reviewer`, and `db-migration-verifier` all checked; only remaining items are a follow-up real-Postgres pass on the explicitly-listed untested pieces (PostgREST introspection, the `party_visible_items` view itself, the full three-way `lots` matrix, pooler JWT propagation, revoke-then-access flow) and both approver signatures.

## General landing page (`/`) formalized; `/dashboard`/`/reports` route collision resolved (2026-08-07)

The product owner requested an additional dashboard page: a general "overview of everything" screen acting as the landing page after login, for all authenticated users, not just office/supervisor roles. This screen already existed as a visual artifact — `05-ui-shell-and-navigation/mockup.md` §1 (floor shell — default route: greeting, "TODAY" task-count summary card, quick actions, one open-work-queue CTA, bottom tab nav) and §3 (office shell — dashboard/review route: per-queue summary cards for Receiving/Picking/Inspection with open/today counts, a Recent Activity table) — but it had never been formalized into `05`'s approved `requirements.md`/`design.md`, and no route in `05`'s route catalog table claimed it.

This surfaced a real path collision: `16-reporting-and-analytics/requirements.md` FR-1.1 already claimed `/dashboard` as "the default landing route," but `16`'s dashboard is a different screen — KPI cards, a 52-week activity heatmap, and a Quick Access panel, explicitly gated by `reporting.read` and explicitly never shown to floor staff (FR-1.1, FR-2.4, §2.4). Had the new general landing page also been built at `/dashboard`, two different screens with two different audiences and two different gating rules would have collided on the same path and name.

**Resolved**: the general landing page owns `/`, and `16`'s analytics dashboard moves to `/reports` — the path `05`'s own route table already reserved for it (`| /reports | office | reporting.read | 16-reporting-and-analytics | Planned |`), so no new route needed to be invented for `16`; it simply now matches what `05` already declared.

Propagated into the owning specs, matching each file's existing formatting and voice, without touching any `Status` header (this is an additive amendment to already-approved specs, the same pattern already used for the Master Inventory addition to `01-core-data-model`):

1. **`05-ui-shell-and-navigation/design.md`**: added a `/` row to §3.2's route catalog table (`shared` surface, `none` capability — the same reasoning already used for `/sync` and `/portal`, `05-ui-shell-and-navigation` as the owning spec, `Launch` status), a prose subsection describing the floor/office content per the mockup and naming the read-only sources (`07`, `08`/pick lists, `11`, `09`) each already gated by their own capability, and a `/` row in §3.3's Surface routing rules table (shared, office-tier for office and `"party"` sessions per the existing `"party"`-reuses-office-shell rule).
2. **`05-ui-shell-and-navigation/requirements.md`**: added `R11` (General landing page) — default post-login destination, per-surface rendering, aggregation of read-only summary data from `07`/`08`/`11`/`09` without duplicating their capability gates, no `capability` value of its own, and an explicit statement that it is not `16`'s `reporting.read`-gated analytics surface. Added a matching acceptance-criteria bullet and a `07`/`08`/`11`/`09` dependency note in §5 — all four are `Approved`, so this is not a blocked dependency.
3. **`16-reporting-and-analytics/requirements.md`**: FR-1.1's route reference corrected from `/dashboard` to `/reports`, with an inline note explaining the correction and reaffirming that FR-1.2–FR-1.5 (KPI cards, trend indicators, heatmap, Quick Access panel) are unchanged — only the path moved. No other FR-1 content was touched.

**Follow-up closed same day**: `16-reporting-and-analytics/design.md` §8.4 (Playwright scenarios) and `tasks.md` (Task 16.4 step 1, Task 16.7 step 1) also referenced `/dashboard` literally and were reconciled to `/reports` immediately after the initial pass above, each with an inline note pointing back to this entry — the same class of stale-cross-reference gap this log has caught and fixed elsewhere in this project (e.g. the `01` `pick_lists`/`wrr_inspection_logs` tasks.md sync gap, the `05` §3.2/§3.3 capability-column/surface-table sync gaps).

No spec's `Status` header was changed and no sign-off box was checked: `05` and `16` remain `Approved` for their prior verified content, with these being additive route/requirement amendments, not reopenings — consistent with the standing product-owner auto-sign-off arrangement for spec documentation of this kind.
