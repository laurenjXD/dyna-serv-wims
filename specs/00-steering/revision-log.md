## `01` real-Postgres verification — FAIL, six spec bugs found and fixed (2026-08-05)

Ran `db-migration-verifier` against `01`'s reconciled schema. Since no `supabase/migrations/` or `lib/db/schema/` exist yet anywhere in the repo, it hand-translated `design.md` §1.1/§1.2 into literal DDL, applied it to a real disposable Postgres 16, and exercised every declared constraint with real INSERT/UPDATE/DELETE statements (not just applying DDL). Result: **FAIL** — the constraint *shapes* that existed behaved correctly (non-negative/committed-within-remaining checks, unique placement rows, immutable-ledger triggers, scoped `lot_number` uniqueness all held under real data), but design.md itself contained six real bugs, all now fixed:

1. **`wrr_items.item_id` was `NOT NULL`, contradicting `design.md` §3 workflow 2's own on-the-fly item enrollment** (a WRR line can reference an item not yet in the catalog at CIPL-encoding time). **Fixed:** made nullable, with a comment pointing to `07`'s design.md §6/§8, which already requires resolved item data as a receipt-confirmation prerequisite — so `01` only needed to stop forbidding the null state `07` already assumes.
2. **No enum existed for `inventory_commitments`/`inventory_commitment_lines.status`** despite tasks.md explicitly requiring "lifecycle, expiry, release, execution" states, unlike every other status column in the schema. **Fixed:** added `commitmentStatusEnum` (`active`, `inspection_pending`, `executed`, `released`, `expired`, `cancelled`), derived from `08`'s already-approved-content Stage 1/2 state descriptions.
3. **`lot_location_balances` and `inventory_commitments`/`inventory_commitment_lines` were specified as prose, not literal Drizzle code**, unlike every other table — column types were implementation-guessed. **Fixed:** converted both to literal TypeScript code blocks with explicit CHECK constraints, matching the rest of §1.2's pattern; `lot_inventory_totals` is now an explicit SQL view definition.
4. **Three code blocks would not compile as written** — missing imports: `items.ts` used `flowTypeEnum`/`parties` without importing either; `lots.ts` used `wrrItems` without importing it; `wrr.ts`'s `wrrInspectionLogs` used `conformanceStatusEnum`/`nonConformanceReasonEnum` without importing either. **Fixed:** added the missing imports. Same failure class as the project's earlier font-substitution and CBM/unit-mismatch bugs — looks right on read-through, breaks on first compile.
5. **`wrr_documents`' code block was missing `peza_number`**, directly contradicting `requirements.md` AC5 ("Both `wrr_documents` and `lots` MUST support `peza_number`"). `lots` had the field; `wrr_documents` didn't. **Fixed:** added the column.
6. **SPQ-multiple enforcement (requirements.md AC7) has no schema-level backing** (confirmed by test: a non-SPQ-multiple `qty` on `pick_list_items` inserted without error) — correct, since this is application-layer validation, but the division of responsibility was undocumented. **Fixed:** added a note in design.md §3 item 9 stating this is enforced by `08`'s allocation engine, not a DB CHECK.

RLS and commitment-function idempotency were reported as "not testable" rather than pass/fail — both are correctly out of scope for `01` (owned by `02` and `08`/`09` respectively). Re-verification against the fixed schema is queued next.

## `02` RBAC/RLS design review — one blocking security gap, several underspecified mechanisms (2026-08-05)

Ran `rbac-rls-reviewer` against `02`'s design.md (no code exists yet; this is a pre-implementation document review). The three-layer UI/server/RLS enforcement posture and most §7.4 patterns (`wrr_documents`, `pick_lists`, parent-inheriting `wrr_items`/`pick_list_items`) were assessed as sound and genuinely enforced-at-data-layer in intent, not just assumed. Six findings needed fixing, all now resolved in design.md:

1. **Blocking security gap**: §3.2 stated null-`flow_type` party scope means "all externally applicable flows," excluding Supplies — but §7.2's `has_party_scope` helper was described as "honoring null as all allowed flows" with no mechanism actually excluding `'supplies'`, and no capability-model rule stopped Supplies resources from being modeled as `assigned_party`-scoped in the first place. A party user with a null-`flow_type` scope on a party that is also a Supplies vendor could pass `has_party_scope(vendor_party_id, 'supplies')` and read internal Supplies data — directly violating requirements.md FR-4.2 and acceptance criterion #7. This was intent-only prose with no enforced mechanism, the exact failure class this review exists to catch. **Fixed** with two independent, redundant gates: `has_party_scope`'s own match logic now explicitly excludes `'supplies'` from null-match; `can_access_party_resource` independently hard-denies any `assigned_party`-scope check where the target row's `flow_type = 'supplies'`, regardless of what `has_party_scope` alone returns. The capability catalog rule is now explicit: Supplies-flow capabilities MUST be `scope_kind = 'global'`, never `assigned_party`.
2. **`lots`/`inventory_transactions` had one uniform `owner_party_id`-based RLS pattern**, but `owner_party_id` is required-and-authoritative for VMI while optional-and-not-the-customer for Trading (the warehouse owns Trading stock pre-sale; the same lot can split across multiple customer pick lists). A uniform policy would either wrongly deny Trading customers their own picked lot or leak an unrelated party's lot. **Fixed**: explicit two-branch policy — VMI uses `owner_party_id`; Trading joins through `pick_list_items.lot_id` → `pick_lists.customer_party_id`; Supplies is never party-scoped (per finding 1's rule). `inventory_transactions` inherits the same branch since it has no direct party column.
3. **`items` party-visibility had no join path specified at all** (unlike every other §7.4 row, which names exact columns). **Fixed**: party-user item visibility is now defined as derived only through `item_id` values reachable via the caller's own scoped `wrr_items`/`pick_list_items` records, excluding `default_supplier_party_id`/pricing fields from that projection — never a direct catalog read, and `default_supplier_party_id` is explicitly barred from ever being used as an RLS predicate (it identifies the warehouse's supplier, not the requesting party).
4. **`SECURITY DEFINER` helper owner/grant strategy was underspecified** — unclear how the helpers read RLS-protected `role_permissions`/`user_party_scopes` without either breaking (too-narrow grants) or over-granting (bypassing everything). **Fixed**: named a dedicated `rbac_definer` owner role with `BYPASSRLS` and table-scoped `SELECT` only on the specific tables these four functions read; ordinary roles get `EXECUTE` on the functions, never direct table access. Also fixed: these helpers must never be exposed as client-callable Supabase RPC endpoints (boolean-oracle enumeration risk) — added an explicit no-RPC-exposure requirement and a real-Postgres test for it.
5. **Last-administrator invariant lock (§8.5) was imprecise enough to permit a still-racy "spec-compliant" implementation**: a per-row lock on only the target administrator being revoked does not serialize against the aggregate count — two concurrent revocations of two *different* administrators can each independently see "1 will remain" and both commit, leaving zero. **Fixed**: specified a single fixed-key `pg_advisory_xact_lock` on a constant identifying the invariant itself, serializing all such operations globally. Also fixed: §8.3 (role revocation) didn't reference the invariant at all, even though FR-7.6 requires it for revocation as well as deactivation, and revoking the `administrator` role is a distinct code path from deactivating the profile — added the missing cross-reference.
6. Minor: §8's admin operations now state explicitly that privileged server functions must independently re-verify the caller's capability rather than trusting an upstream `requirePermission()` call; §6.3's transaction wrapper now states rollback must be guaranteed via try/finally on callback exception.

`02`'s Sign-off section remains fully unchecked pending real-Postgres tests of these fixes (now added to §13's testing design) and both approver sign-offs.

## `03-offline-mode-and-client-storage` — stale terminology and a real Tier 1/2 boundary violation (2026-08-05)

`requirements.md` was already clean, but `offline-sync-reviewer` found `design.md` written against a pre-reconciliation version of the schema, with two classes of problem:

**Terminology drift**, now fully renamed: `po_id`/`sku_id` (no PO/SKU concept exists — inbound is WRR-based, `item_id` is the canonical term) → `wrr_id`/`item_id`; `withdrawal_line` (no separate withdrawal-request entity — outbound is `pick_lists`/`pick_list_items`) → `pick_list_item_id`/`inventory_commitment_lines`; `lots.qty_committed` (quantity/commitment state lives on the child table, not `lots`) → `lot_location_balances.qty_committed`; `lots.status = "under_inspection"` (not a valid `lot_status` value — inbound inspection precedes lot existence and is tracked in `wrr_inspection_logs`) → removed; a "Manager" role (`02`'s four roles are `warehouse_staff`/`supervisor`/`administrator`/`party_user`, no "Manager") → corrected.

**Real Tier 1/2 boundary violation**: three of the four actions §5.1 listed as "safe to queue offline" — `lot_create`, `placement_override` (putaway), `qi_outcome` (inspection resolution) — directly contradicted `07-incoming-receiving/design.md` §10, which already states lot creation, putaway confirmation, and inspection resolution are Tier 2/online-only, and §8, where lot creation happens only inside `07`'s single locked confirm-receipt transaction. The fourth, `scan_confirm`, conflated Stage 2 dispatch *capture* (safely Tier 1 per `08` §10) with the *decrement itself* (`08` places this in Tier 2, since it also gates document generation). Concrete failure scenario for `lot_create` alone: a device could scan a carton offline before an inspector (working online, on a different device) flags that same carton `non_conformance`, then replay `lot_create` on reconnect and create an `available` lot for stock that should have been quarantined — bypassing `07`'s atomic inspection-gates-availability guarantee.

**Fixed**: replaced all four action types with two pure-capture Tier 1 types — `wrr_scan_capture` (records a barcode scan against an expected WRR line; never creates a lot) and `pick_scan_capture` (records a dispatch scan against a committed pick-list item; never decrements a balance). Lot creation, putaway, inspection resolution, and final dispatch are now explicitly Tier 2, non-queued, operator-submitted-only commands — rewritten throughout §4.5 (outbox schema), §5.1 (safe/unsafe tables), §6.3 (removed a now-obsolete cross-entry ordering note that only existed because `lot_create` was wrongly queueable), §6.4 (`/api/sync` validation table rewritten against current schema), and §9.2 (page-behavior table no longer implies putaway/inspection/dispatch "worked" while offline when only a scan was captured). Also clarified §7's idempotency mechanism (the outbox entry's client-generated `id` is the actual unique-constraint/upsert key on the server write, not a separate idempotency-log table) since the review found this ambiguous enough to under-specify.

`03`'s Sign-off/testing status was already fully open; this closes the design-level gap ahead of any implementation, before the wrong boundary could get built.

## Claude Code alignment

**Explicit limitation, not glossed over**: subagent tool restrictions in Claude Code are per-tool (Read/Write/Bash/etc.), not per-file-path. The `spec-writer` agent's lack of Bash access is a real technical restriction; its instruction to only write inside `specs/` is a followed convention, not a hard technical boundary. Same class of limitation as the "no code before approved tasks.md" rule itself — enforced by an agent choosing to follow it, not by the tooling refusing otherwise.
