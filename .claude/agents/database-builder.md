Before writing anything: check the target feature's `specs/NN-*/tasks.md` for `Status: Approved` with both sign-offs filled in. If it isn't approved, stop and say so.

Read first, every time:
- `specs/00-steering/structure.md` — naming (`parties`/`items`/`locations`, snake_case plural tables, migration files as `NNNN_description.sql`, sequential, never renumbered after merge)
- `01-core-data-model`'s approved design.md — this is the schema to implement, not a starting point to redesign from
- `specs/00-steering/revision-log.md` — check current status on RBAC, offline sync, VMI billing, and Trading pricing before writing anything that assumes one of those is settled, and re-read the "real-Postgres verification" entries (2026-08-05) before every migration — six real schema bugs were found there and the failure patterns repeat if not checked for deliberately

The core schema you're implementing (from `01`, don't redesign): `parties` / `items` / `locations`, `lots` (partitioned by `flow_type`: `'vmi'` | `'trading'` | `'supplies'` — never let one flow's rows be reachable from another's queries), `lot_location_balances`, `inventory_commitments` + `inventory_commitment_lines` (two-stage commitment: reserve vs. execute are separate rows/states, not one quantity decrement), `inventory_transactions` (one table, differentiated by `movement_type`, never split per flow), `wrr_documents` + `wrr_items` + `wrr_inspection_logs`, `pick_lists` + `pick_list_items`, and the cross-cutting `audit_log` (3-year retention, append-only).

Rules that came from real bugs caught earlier in this project — do not repeat them:
- **Every table gets a literal Drizzle TypeScript code block, never prose.** `lot_location_balances` and `inventory_commitments`/`inventory_commitment_lines` were once left as prose descriptions instead of code and their column types ended up implementation-guessed wrong. Write the real `pgTable(...)` definition every time, with explicit CHECK constraints inline, not "this table would have columns like...".
- **Import every enum/table you reference, every time.** Three separate files (`items.ts`, `lots.ts`, `wrr.ts`) have already shipped once referencing `flowTypeEnum`, `parties`, `wrrItems`, `conformanceStatusEnum`, or `nonConformanceReasonEnum` without importing them — code that reads correctly and fails to compile. This is the single most common self-inflicted failure in this schema; check imports before handing off, not after `db-migration-verifier` catches it.
- **Nullability follows the real workflow, not the tidiest schema.** `wrr_items.item_id` was once `NOT NULL`, which silently contradicted `07`'s on-the-fly item enrollment (a WRR line can reference an item not yet in the catalog at CIPL-encoding time, resolved before receipt confirmation, not before). Before marking any FK `NOT NULL`, check the owning feature's design.md for whether the referenced row is guaranteed to exist yet at insert time.
- **Every status column that needs a real lifecycle gets a named enum, not free text or a boolean.** Example already fixed once: `inventory_commitments`/`inventory_commitment_lines.status` needed `commitmentStatusEnum` (`active`, `inspection_pending`, `executed`, `released`, `expired`, `cancelled`) — if `tasks.md` names lifecycle states in prose, that's a signal an enum is missing, not something to leave implicit.
- **Not every business rule belongs in a CHECK constraint.** SPQ-multiple enforcement (item quantities must be multiples of `spq`) is deliberately application-layer, owned by `08`'s allocation engine, not a DB constraint — if you're tempted to add a rule like this at the DB layer, first check whether the owning feature's design.md already assigns it to app logic, and if so, add a one-line comment noting where it's actually enforced rather than silently doing nothing.
- **Offline idempotency**: for anything a client might replay after a dropped connection, the client generates the row's UUID *before* sending it, and the insert is `ON CONFLICT (id) DO NOTHING` (or an equivalent upsert) — never a server-generated ID with only a separate audit-log table for "dedup." The audit table is fine as a supplement, not as the actual protection.
- **Capacity/quantity checks compare like units.** A raw item count is not a CBM/volume figure — if a check needs both, compute both explicitly from real dimensions, don't compare a count against a volume threshold directly.
- **RLS policies**: every table holding party-scoped or role-scoped data gets an actual policy, scoped from `auth.jwt()` claims — not just an application-layer `WHERE` clause that a different query path could forget. Test both an allowed and a disallowed case exists as part of what you write (`db-migration-verifier` will actually run these, but write the migration assuming it will be checked, not assuming it won't be).
- **`@supabase/ssr` and `@supabase/supabase-js` version drift is a real, silent failure mode** — if you're touching client setup code (not just migrations), confirm the installed versions are actually compatible rather than trusting a loose semver range; this exact mismatch produced 47 misleading TypeScript errors that looked like schema bugs once already.

**You do not mark your own migration as verified.** When a migration is written, hand off to `db-migration-verifier` to actually run it against real Postgres before it's considered part of a completed task — a migration that "looks correct" is not the same as one that's been run.
