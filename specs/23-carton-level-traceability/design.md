# Carton-Level Traceability — Design

Status: Approved

## Dependencies

Depends on `01-core-data-model`, `07-incoming-receiving`,
`08-outgoing-withdrawal-and-two-stage-commitment`, `10-pick-list-and-
acknowledgement-receipt`, and `18-barcode-integration`. Existing tables remain
authoritative for items, lots, WRRs, inventory balances, transactions, and
exact physical units.

## Persistence

Add `carton_id` to `inventory_units` as the stable human-readable identity,
backfilled deterministically for existing rows. Add `carton_status_history`
with `(carton_id, changed_at, id)` ordering and immutable previous/new status,
quantity, location, source transaction, actor, reason, and override actor.
Add `receiving_exceptions` and `receiving_exception_lines` for expected versus
actual carton and quantity variance. Carton IDs are generated by a database
sequence-backed function with the `DSGC-CTN-YYYYMMDD-NNNNNN` format, while
supplier-provided IDs may be retained after uniqueness validation.

The current `inventory_units.status` values remain valid for exact-pick
execution. The carton lifecycle is represented by the new history/status
contract and mapped to existing unit states at receiving and picking seams;
no second quantity authority is introduced.

## Command boundaries

- `registerCarton`: receiving-authorized, source WRR line required unless an
  explicitly authorized manual-registration policy is later approved.
- `recordCartonScan`: receiving scan authorization, idempotent under a unique
  carton/WRR relationship, returns named validation outcomes.
- `recordCartonStatus`: only owning workflow commands may change status; every
  change writes history in the same transaction.
- Existing pick/dispatch commands continue to own reservation and inventory
  transaction changes and gain Carton ID validation as a prerequisite.

## Validation order

Resolve identifier → lock carton/receiving relationship → validate shipment,
item, owner, warehouse, status, and duplicate relationship → write scan and
status history → update existing receiving counters. Any failure rolls back
the mutation and returns `What happened`, `Why`, and `Next action` data.

## UI

Receiving gets a scanner-ready carton field, large progress counters, and
explicit valid/duplicate/wrong-item/unknown/over-receipt feedback. Stock and
pick views display Carton ID as an identifier and disclose history/details on
request. Labels can render QR and Code 128 through the shared barcode layer.
