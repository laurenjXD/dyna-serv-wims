## 1. Purpose and scope

This feature is the external-facing self-service surface for `parties` — VMI vendors and Trading/3PL customers — authenticated under the `party_user` role defined in `02-rbac-roles`. It is the party-facing counterpart to `06-party-and-item-enrollment` (internal master-data administration) and to `21-user-profile-and-settings` (internal-staff-facing account/settings surface, whose generic `/profile` route a party user also uses for personal account fields).

It defines what a party user sees and can do once authenticated:

- Their own VMI live inventory position (occupied CBM / lot balances) or their own Trading order/document history, scoped to their assigned party/flow.
- Their own generated documents (pick lists, acknowledgement receipts, and — pending a capability-catalog decision named in §7 — VMI billing statements).
- Their own scoped in-app notifications.
- A party-switcher when a user's `user_party_scopes` assignments span more than one active party and/or a narrowed `flow_type`.

It does not define the RBAC/role model itself, master-data enrollment, VMI billing calculation, Trading pricing calculation, document generation/artifact pipeline, or the shared UI shell — it consumes all of those as approved contracts and cites their tables/mechanisms by exact name, never redefines them.

## 2. Terminology and ownership boundaries

- A `party` is a vendor, customer, or end-customer record in the shared `parties` table (`01-core-data-model`). This spec never introduces a parallel "portal user" or "external account" entity — a party user is a `user_profiles` row per `02`, bound to one or more `parties` rows through `user_party_scopes`.
- `flow_type` (`vmi`, `trading`, `supplies`) is the partition key on `lots`/documents. Per `02` design.md §3.2 and §7.4, Supplies is never party-scoped under any circumstance — this portal never renders or queries Supplies-flow data for a party user. This is the single most safety-critical boundary in this spec and is restated throughout.
- `pick_list` and `acknowledgement_receipt` are the two priced outbound documents (`10-pick-list-and-acknowledgement-receipt`). No `withdrawal_slip`, no `awaiting_pricing` status.
- Trading's price on a document is final. VMI's price on a document is a per-release reference only — the authoritative VMI bill is always the period average `vmi_billing_statement` (`12-vmi-billing`), never a single document's total.
- Personal account fields (display name, contact number, password reset, UI preferences) belong to `21-user-profile-and-settings`'s `/profile` route, which a party user also uses. This spec does not redefine that route; it only defines the party-scoped business-data surfaces (inventory position, documents, notifications, party-switcher) that are unique to the `party_user` role.
- Business classifications on `parties` (`party_roles` — `vendor`, `supplier`, `customer`, `end_customer`, `internal_warehouse`) are never application-user roles. This spec consumes them for display only (e.g. confirming a party's VMI vs. Trading classification for UI framing); it never mutates them.

## 3. Actors and surfaces

- **Party users** (VMI vendors, Trading/3PL customers) are the sole actor for this feature. A party user may be assigned to one or more `parties` rows, and each assignment may optionally be narrowed to one `flow_type` (`02` decisions 1E=B, 1F=B). The portal must support this from day one — it must not assume one party per user or one flow per party.
- **Internal staff** (warehouse staff, supervisors, administrators) do not use this portal surface; their views into a party's inventory/documents are owned by other specs (`16-reporting-and-analytics`, `06`, `09`). This spec does not define an internal "view as party" mode.
- The portal is external, office/desktop-first, but must remain usable on mobile — it is not a floor scan flow (see §8/R9).

## 4. Functional requirements

### R1. Authentication and party context

1. A party user SHALL authenticate through the same Supabase Auth session mechanism as internal staff, per `02-rbac-roles`; this spec does not define a separate authentication path.
2. WHEN a request is made against this portal, THE SYSTEM SHALL resolve the user's active `user_party_scopes` assignments server-side, SO THAT no client-supplied party ID, flow, or role is ever used as the basis for which data is shown.
3. WHEN a party user has exactly one active party/flow assignment, THE SYSTEM SHALL default the portal context to that assignment, SO THAT the user reaches their data without an extra selection step.
4. WHEN a party user has more than one active `user_party_scopes` assignment (multiple parties, and/or the same party narrowed to different `flow_type` values), THE SYSTEM SHALL present an explicit party/flow switcher, SO THAT the user can select which scoped context they are viewing, and every subsequent read in this feature SHALL be re-scoped server-side to the selected assignment, not merely filtered client-side.
5. THE SYSTEM SHALL NOT allow a party user to view combined/aggregated data across two parties or two flow scopes in a single request — each read is scoped to exactly one active assignment at a time.
6. WHEN a party user's assignment is narrowed to a single `flow_type`, THE SYSTEM SHALL hide the surfaces (VMI position, Trading documents) that do not apply to that flow, SO THAT a Trading-only party user is never shown a VMI inventory-position screen for the same party, and vice versa.
7. THE SYSTEM SHALL additionally resolve the caller's own `party_roles` rows as part of context resolution, using the already-granted self-row `parties` read (R5.2; `02` design.md §7.4: "`party_roles` visibility inherits from the parent `parties` row — a row is readable iff the caller satisfies the `parties` select policy for the same `party_id`") — no new capability or RLS mechanism is introduced by this clause. THE SYSTEM SHALL determine inbound-supplying eligibility as "the active party has at least one `party_roles` row with `role IN ('vendor', 'supplier')`," SO THAT R11's barcode-pre-labeling entry point is shown/available only for an assignment that actually qualifies. A VMI assignment is inherently inbound-supplying by the flow's own definition (VMI has no downstream "customer" concept — the vendor owns the stock, per `product.md`), so this distinction only has to be evaluated for Trading assignments.
8. **Party-switcher persistence (product owner decision, 2026-08-06): session-only in v1.** THE SYSTEM SHALL NOT persist a "last selected" party/flow preference across sessions. A party user with more than one active `user_party_scopes` assignment SHALL be presented the explicit switcher (R1.4) at the start of every new session; a party user with exactly one active assignment continues to receive the auto-default (R1.3) every session. This avoids creating a build dependency on `21-user-profile-and-settings`'s UI-preference mechanism before `21` itself is approved, and is the lower-risk/simpler default — session-only persistence can be extended to cross-session persistence later as a pure enhancement, with no breaking change to this baseline.

### R2. VMI inventory position (VMI-scoped parties only)

1. WHEN a party user's active assignment includes `flow_type = 'vmi'` (or an unnarrowed/null-`flow_type` assignment, which per `02` §3.2 excludes Supplies but includes VMI), THE SYSTEM SHALL display a live inventory-position view of the party's own VMI-owned lots, SO THAT the vendor can see their current occupied stock without contacting the warehouse.
2. THE SYSTEM SHALL source this view from a scoped `lot_location_balances` read joined one-hop to the parent `lots` row, authorized per `02` design.md §7.4's VMI pattern: `can_access_party_resource('lot_location_balances', 'read', lots.owner_party_id, 'vmi')`. This spec does not define a new query pattern; it consumes this exact mechanism.
3. THE SYSTEM SHALL NOT display a Trading party user's or an unrelated VMI party's balances under any request.
4. The view MAY show item identity fields (code, name, description, UOM, `volume_cbm`) sourced only through the approved party-safe projection (see R5) — it SHALL NOT expose `default_supplier_party_id`, `buying_price`, `selling_price`, or `min_reorder_level`.
5. THE SYSTEM SHALL NOT provide a party-user-initiated inventory mutation (adjustment, reconciliation, transfer request) anywhere in this view — it is read-only.
6. THE SYSTEM SHALL NOT expose `inventory_transactions` directly to a party user under any circumstance, consistent with `02` design.md §7.4 ("no direct party column and no party-user grant in v1").

### R3. Trading order/document history (Trading-scoped parties only)

1. WHEN a party user's active assignment includes `flow_type = 'trading'` (or an unnarrowed/null-`flow_type` assignment), THE SYSTEM SHALL display the party's own `pick_lists` (as `customer_party_id`) with status and document links, SO THAT the customer can track order/dispatch state.
2. THE SYSTEM SHALL source lot/location detail shown on a Trading order (lot number, location label) exclusively from the frozen snapshot fields already present on the party's own `pick_list_items` rows (`lot_number`, `location_label`, per `01-core-data-model`'s `pick_list_items` schema and `10`'s document-snapshot model) — never a live join to the shared `lots` row, consistent with `02` design.md §7.4's explicit rejection of a `pick_list_items`-join pattern for `lots` access.
3. THE SYSTEM SHALL NOT expose `inventory_commitments` or `inventory_commitment_lines` to a party user; dispatch/commitment status is surfaced only through the party's own `pick_lists` document state, per `02` design.md §7.4.
4. THE SYSTEM SHALL display only the final Trading document price already frozen onto the party's own `pick_list_items`/acknowledgement-receipt records (owned by `13-trading-orders-and-pricing`'s price-resolution logic and rendered via `10`'s snapshot). It SHALL NEVER display margin, buying cost, or any field gated behind `trading.margin_view` (admin/supervisor only, per `13` requirements.md's resolved margin decision).
5. THE SYSTEM SHALL NOT provide a party-user-initiated order-creation, price-negotiation, or FIFO-override-request action anywhere in this view.

### R4. Documents (pick lists, acknowledgement receipts, VMI statements)

1. THE SYSTEM SHALL let a party user list and open their own generated documents (`pick_list` and `acknowledgement_receipt`) using the `documents.read` (`assigned_party`) capability from `02`'s finalized catalog.
2. THE SYSTEM SHALL serve every document as a short-lived (≤60-minute, per `04` design.md's Storage access section) signed URL, re-authorized server-side on every access request — never a durable public link, consistent with `10` requirements.md R5.
3. THE SYSTEM SHALL preserve, not strip, the mandatory VMI acknowledgement-receipt disclaimer defined by `10`/`12` ("Unit prices are per-release reference values only. Authoritative billing is the period VMI statement.") — the portal renders the document artifact as generated; it does not re-template or omit disclaimer content.
4. WHEN a VMI party user requests to view/download their own issued `vmi_billing_statement` records and `vmi_credit_notes` status, THE SYSTEM SHALL do so, gated by `vmi_statements.read` (`assigned_party`) — **added to `02`'s finalized capability catalog (2026-08-06)** (`02` design.md §3.2/§7.4), covering both `vmi_billing_statement` and `vmi_credit_notes` reads scoped to the statement's/note's owning `party_id`, SELECT-only for `party_user` with no INSERT/UPDATE/DELETE (both tables remain `12-vmi-billing`'s exclusively server-generated domain). This is no longer an open capability-catalog gap; it is subject to `02`'s own normal approval/sign-off process (including `rbac-rls-reviewer` coverage) completing for this addition — the same distinction already drawn for R11's barcode-pre-labeling blockers.
5. THE SYSTEM SHALL NOT allow a party user to view another party's document by ID guessing, filter manipulation, count inference, or URL reuse — every document read is re-authorized against the current session's active party/flow scope on every request, per `10` requirements.md R7.3.
6. A `vmi_billing_statement` with `status = 'voided'` SHALL NOT be presented as the current/payable statement; if displayed at all (e.g. in a history list), it SHALL be clearly marked voided and SHALL link to its superseding statement via `supersedes_statement_id` where one exists.
7. **v1 statement depth: PDF artifact only (product owner decision, 2026-08-06).** A VMI party user viewing their own `vmi_billing_statement`/`vmi_credit_notes` records sees the generated PDF artifact only, via the same signed-URL document mechanism as R4.2 — no structured native line-item/per-charge-type rendering in the portal for v1. This is consistent with this portal's existing document-handling pattern everywhere else (documents are rendered as generated, never recalculated or re-presented in structured form by the consuming feature) and avoids duplicating `12-vmi-billing`'s own billing-calculation display logic into a second UI surface before `12` itself has finalized one. A structured native breakdown is explicitly deferred as a future enhancement, not designed here.

### R5. Item and party self-data visibility

1. THE SYSTEM SHALL NOT grant a party user any direct `SELECT` on the base `items` table. Item identity fields shown anywhere in this portal (VMI position, Trading document lines) SHALL be sourced exclusively through the `party_visible_items` view (owned as an `02`-designed RLS mechanism, populated from `06`'s domain data), which never exposes `default_supplier_party_id`, `buying_price`, `selling_price`, or `min_reorder_level`.
2. THE SYSTEM SHALL let a party user read their own `parties` master-data row (name, code, contact fields, address) via the implied self-row read `can_access_party_resource('parties', 'read', id, null)` (`02` design.md §7.4), SO THAT the party can confirm their own record — this is read-only; the party user cannot edit their own `parties` row through this feature (master-data edits remain `06`'s domain, administrator-only).
3. THE SYSTEM SHALL NOT let a party user read another party's `parties` row, `party_roles`, or any derived aggregate that could reveal another party's existence or business classification.

### R6. Notifications

1. THE SYSTEM SHALL provide a party-scoped in-app notification center reusing `14-notifications-and-alerts`'s existing contract (unread count, category/severity filters, read/dismiss state, safe navigation links) rather than defining a competing notification model.
2. Recipients SHALL be computed server-side from the user's current `notifications.read` (`assigned_party`) capability and active party/flow scope — never client-filtered from a global stream, per `14` requirements.md R2/R6.
3. THE SYSTEM SHALL NOT surface a notification whose linked resource the party user cannot currently open (revoked scope, wrong flow, wrong party) — link resolution re-authorizes on open, per `14` requirements.md R6.2.

### R7. Authorization and audit

1. Every protected read in this feature SHALL use the capability-and-scope interface from `02-rbac-roles` (`pick_list.read`, `documents.read`, `notifications.read`, and the implied self-row `parties.read`, all `assigned_party` scope kind), plus the proposed `vmi_statements.read` (`assigned_party`) pending `02` approval per R4.4.
2. THE UI MAY hide unavailable surfaces (e.g. hide the VMI position tab for a Trading-only assignment), but the server and RLS SHALL enforce the decision independently.
3. Client-supplied party ID, flow, role, or capability values SHALL NEVER establish authorization anywhere in this feature.
4. THE SYSTEM SHALL NEVER render or query Supplies-flow (`flow_type = 'supplies'`) data for a party user under any circumstance — enforced by `02`'s two independent gates (`has_party_scope` null-`flow_type` exclusion + `can_access_party_resource` hard-deny), which this feature consumes but does not re-implement or weaken.
5. Document opens, statement views, and notification reads/dismissals SHALL be attributable to the actor and correlation ID through the approved audit boundary owned by `04`/`14`/`10`.

### R8. Offline and realtime behavior

1. THE SYSTEM SHALL treat every surface in this portal as fully online-only. This portal is not a floor/scan workflow and has zero Tier 1 offline-queue eligibility — unlike specs that at least discuss a boundary (`06`, `13`), this portal simply has no offline surface to design.
2. THE SYSTEM SHALL NOT cache party inventory position, document content, or billing statement data for offline access; every view is a fresh authoritative read on load.
3. Realtime updates (if enabled for notification count refresh) MAY invalidate/refresh a list, but the client SHALL refetch authoritative records and SHALL NOT treat an event as authorization or as the complete record.

### R9. Accessibility and responsive behavior

1. This portal is office/desktop-first (like `06`'s enrollment surface) but SHALL remain fully usable at the approved mobile breakpoint — it is explicitly NOT a floor/scan flow, so mobile-first floor rules (64px scan-primary buttons, thumb-zone primary action, single-primary-action-per-screen) do NOT apply here; standard office/desktop contrast (AA), touch targets (44px), and hover/press rules from `brand-design-system.md` apply instead.
2. The portal SHALL follow the approved brand tokens, typography, contrast, touch targets, motion, and no-color-only status rules.
3. Every list/detail view SHALL provide labels, keyboard navigation, visible focus, and programmatic error association.

### R10. Party-scoped data analytics

1. WHEN a party user's active assignment includes `flow_type = 'vmi'` (or an unnarrowed/null-`flow_type` assignment), THE SYSTEM SHALL surface a party-scoped VMI analytics view covering occupied CBM over time, stock-on-hand summary, lot activity summary, and the VMI billing-period reference banner, exactly as defined by `16-reporting-and-analytics` requirements.md FR-5 ("a party user sees only their own party"), SO THAT the vendor can see their own trend/summary data without contacting the warehouse.
2. WHEN a party user's active assignment includes `flow_type = 'trading'` (or an unnarrowed/null-`flow_type` assignment), THE SYSTEM SHALL surface a party-scoped Trading analytics view covering order activity trend and item movement velocity, exactly as defined by `16` requirements.md FR-6, SO THAT the customer can see their own order/movement trend data.
3. THE SYSTEM SHALL NEVER display margin, buying cost, `selling_price`, or any field gated behind `16`'s FR-6.3 margin-reference display to a party user — FR-6.3 itself states "party users never see pricing fields," and this portal SHALL NOT weaken that exclusion.
4. THE SYSTEM SHALL source every chart/table in this view exclusively by embedding `16`'s existing reusable component library (FR-9: `<KpiCard>`, `<KpiCardGroup>`, `<TrendLineChart>`, `<BarChart>`, `<DonutChart>`, `<StockLevelTable>`, `<AlertBanner>`, `<RecentActivityFeed>`) against `16`'s already-party-scoped queries. This spec does not define a new chart component, a new aggregation query, or a parallel analytics engine — it only defines which of `16`'s existing party-scoped views appear in this portal's navigation, and lets the flow-based switcher (R1.4/R1.6) select VMI analytics vs. Trading analytics the same way it already selects the inventory-position vs. order-history surface.
5. THE SYSTEM SHALL NEVER surface Supplies-flow analytics to a party user, consistent with `16` requirements.md §2.3/§2.4 and this spec's own R7.4 Supplies-exclusion rule.
6. **Resolved (product owner, 2026-08-06): `reporting.read` (`assigned_party`) added to `02`'s capability catalog.** `02` design.md §3.2 now carries a `reporting` | `read` | `assigned_party` | `party_user` row, coexisting with the existing `global`-scope `reporting` row, the same pattern already used for `pick_list.read`/`documents.read`/`notifications.read`. No new RLS predicate was needed at the table level: `16`'s party-scoped analytics queries read from `lot_location_balances`, `pick_lists`, and `items` (`party_visible_items`), all of which already have party-scoped RLS patterns defined in `02` §7.4 for other capabilities — `reporting.read` (`assigned_party`) is a server-side authorization gate on top of those already-enforced table policies, not a new RLS mechanism. This is no longer an open capability-catalog gap; it is subject to `02`'s own normal approval/sign-off process completing for this addition, the same distinction already drawn for R4.4's `vmi_statements.read` resolution and R11's barcode-pre-labeling blockers.

### R11. Supplier-initiated barcode pre-labeling of inbound dispatches

Product owner decision (2026-08-06): this moves from future scope into current v1 scope. Purpose: a party in the **inbound-supplying role** — a VMI vendor, or a Trading `vendor`/`supplier` (per `01-core-data-model`'s `party_roles` enum) — generates and prints a barcode label for their own outbound dispatch to the warehouse, so the shipment is already labeled and scan-ready on arrival, without warehouse staff needing to generate the label reactively during receiving (which is `18-barcode-integration`'s current FR-3 behavior). Gated on the caller's active assignment satisfying R1.7's inbound-supplying `party_roles` check.

**Symbology (product owner decision, 2026-08-06)**: v1 uses a **1D linear barcode** (e.g. Code 128), not a 2D QR code. The design is architected so a future migration to QR is a symbology/rendering change only, not a data-model or lookup-mechanism rework — see R11.7.

**Scope boundary (product owner decision, 2026-08-06)**: this capability is available only for items already reachable through the existing `party_visible_items` visibility path (i.e. an item with at least one prior `wrr_items` or `pick_list_items` row for that party — the same reachability rule `02` §7.4 already defines, unchanged). A truly first-ever shipment of a brand-new item continues through the standard back-office-staged `07` flow exactly as it works today, without pre-labeling; no pre-label capability is available for it. This scope boundary relies on `06`'s administrator-only enrollment process as the gate for genuinely new items, per `06-party-and-item-enrollment` — it is a scope narrowing, not a new engineering mechanism. Once an item's first shipment is received (creating its first `wrr_items` row for that party+item pair), every subsequent shipment of that item becomes eligible for this feature automatically.

1. THE SYSTEM SHALL NEVER expose this capability to a Trading `customer`/`end_customer` party — a customer only ever receives from the warehouse and has no outbound dispatch to label. This surface SHALL be reachable only when the caller's active assignment satisfies R1.7's inbound-supplying `party_roles` check (`vendor` or `supplier`).
1a. **Hybrid-party exclusion (added 2026-08-06, `rbac-rls-reviewer` finding B).** A party that holds **both** an inbound-supplying role (`vendor`/`supplier`) **and** a customer-facing role (`customer`/`end_customer`) SHALL NOT be eligible for this feature in v1, even though it independently qualifies under R1.7's vendor/supplier check — `02` design.md §7.4's RLS gate for `shipment_labels.generate`/`wrr_advance_notices` requires the party hold zero `customer`/`end_customer` roles, not merely at least one qualifying role. This is a deliberate scope narrowing, not an oversight, consistent with this repo's established pattern of treating rare edge cases as out-of-scope-for-now (the same reasoning already applied to R11's brand-new-item chicken-and-egg resolution, §7 item 6). If a hybrid vendor+customer party needs this capability, it must be resolved administratively — splitting the party into separate records, or a manual back-office-generated label — not through a portal feature or new RBAC machinery.
2. WHEN an inbound-supplying party user opens the label-generation surface, THE SYSTEM SHALL present a deliberately thin form — **item** (selected from the party's own known items, limited to items reachable through `party_visible_items` per the scope boundary above), a **quantity for this specific label** (per carton/pallet, declared for labeling purposes only), and the **supplier's own lot number** (optional) — and no other field (no expiry, no weight, no dimensions, no disposition), SO THAT this form never becomes a second source of truth alongside the CIPL and the physical count at receiving, consistent with this repo's single-authoritative-source-per-fact pattern (Trading price finality, VMI billing period-average vs. document reference, immutable document snapshots).
3. THE SYSTEM SHALL treat the declared quantity on this form as explicitly NOT authoritative. `07-incoming-receiving`'s existing scanned-vs-expected discrepancy handling (R3.2, R3.3) SHALL still run unchanged at physical receipt regardless of what the label declares. The UI SHALL state this non-authority explicitly and prominently, the same way `12`'s VMI reference-price-vs-authoritative-bill distinction is stated prominently elsewhere in this spec.
4. THE SYSTEM SHALL treat the supplier's own lot number as safe to collect on this form (unlike quantity): per `structure.md`'s glossary, `lot_number` is "Business lot number sourced from the WRR" — i.e. the supplier's own identity data they already own before shipping, not a quantity claim that can drift from a physical count.
5. WHEN a party user submits this form, THE SYSTEM SHALL write a new, narrowly-scoped record — proposed name `wrr_advance_notices` (or similar). This is a **confirmed design direction** (product owner, 2026-08-06); it requires the standard `01`/`07` schema-amendment and approval process before implementation, following the same pattern `07` itself already used when it added `disposition` to `wrr_items` via a noted schema amendment — a settled design choice awaiting formal schema amendment, not an open design question. THE SYSTEM SHALL NOT grant `party_user` any write path into `wrr_items` or WRR creation — `07` requirements.md R1.1 explicitly reserves WRR creation to "an authorized back-office user," and this requirement SHALL NOT create a bypass of that boundary. The party's submission is advisory pre-staging input only.
6. THE SYSTEM SHALL gate this write under the capability `shipment_labels.generate` (`assigned_party`), granted only where the caller's assignment satisfies R1.7's inbound-supplying `party_roles` check — **added to `02`'s catalog (2026-08-06)** (`02` design.md §3.2/§7.4), the same catalog-addition pattern followed for `vmi_statements.read` (R4.4) and `reporting.read` (R10.6), pending `02`'s own approval/sign-off process. Named `shipment_labels.generate` rather than `qr_labels.generate` to stay format-neutral, consistent with this spec's `resource.action` naming pattern (`pick_list.read`, `vmi_statements.read`, `reporting.read`) and with the fact that v1's symbology is 1D, not QR.
7. THE SYSTEM SHALL encode the generated barcode as a UUID pointer to the new advance-notice record, not an embedded data blob, consistent with `18` requirements.md FR-3.2's existing UUID-lookup principle. Since 1D/linear symbologies are inefficient for structured payloads, v1 encodes a flat string identifier — a prefixed form of the `wrr_advance_notices.id` UUID, e.g. `WAN:<uuid>` — rather than embedded JSON. The *referenced record* is identical to what a future QR code would reference: a future migration to QR only changes the label's rendering/encoding format (symbology), never the underlying data model or lookup mechanism. This is explicitly distinct from `18`'s current `{"type": "lot", "id": "uuid"}` payload, since no `lots` row exists pre-receipt.
8. **Confirmed matching flow (product owner, 2026-08-06)**: (a) the party submits the thin form, creating a `wrr_advance_notices` row in a `pending_review` (or equivalent) state; (b) back office reviews it against the actual CIPL they've separately received and either confirms it (creating/matching a staged `wrr_items` line, carrying over item/quantity/party reference — the advance notice's declared quantity is non-authoritative input the back-office user can adjust) or rejects/flags it as a discrepancy for manual follow-up; (c) the physical barcode at the receiving bay is scanned per `07`'s existing R3 barcode-reconciliation flow, resolving to the advance notice's linked `wrr_items` line; (d) if the advance notice was never confirmed by back office before the shipment physically arrives, the scan produces `07`'s existing "unknown/unmatched" exception path (R3.3) rather than a new bespoke error state. `07` continues to own WRR creation exactly as before; this requirement never bypasses that ownership. This is the settled mechanism; it requires `07` to formally write it into its own `requirements.md`/`design.md` before implementation — a procedural gate, not an open design question.
8a. **Self-review prohibition (added 2026-08-06, `rbac-rls-reviewer` finding).** THE SYSTEM SHALL NOT allow the same identity to both submit an advance notice (as a `party_user`) and confirm/reject it (as internal staff). Because `02`'s role model does not make `party_user` and internal-staff role grants mutually exclusive on one account, this SHALL be an explicit, server-enforced check — comparing the confirming/rejecting actor against the submitting party_user's captured identity (`wrr_advance_notices.submitted_by_user_id`, added to `01`'s schema for this purpose) — mirroring `02` §3.4's existing self-approval prohibition for `fifo_override.approve`, not assumed from organizational role separation alone.
9. THE SYSTEM SHALL treat this submission as online-only (Tier 2) — it SHALL NEVER enter the Tier 1 offline queue, consistent with every other online-only mutation pattern in this repo (`06`, `13`).
10. THE SYSTEM SHALL follow the same online-only, capability-gated, audited server-action mutation pattern already established elsewhere in this repo (e.g. `06`'s create-command boundary) for this write — it SHALL NOT be treated as a lightweight exception to this portal's otherwise read-only posture. This is this portal's first mutation; every other capability in this spec remains explicitly read-only.
11. **This requirement is BLOCKED**, but as of 2026-08-06 all four items below have moved from *open design questions* to *written into their owning specs, pending those specs' own normal approval/verification process* — this is a narrower, more precise blocker than the original one: (a) the proposed `shipment_labels.generate` (`assigned_party`) capability and its RLS pattern, restricted to inbound-supplying `party_roles` values, is now written into `02-rbac-roles` design.md §3.2/§7.4 — BLOCKED pending `02`'s normal approval/sign-off process completing for this addition, plus its own `rbac-rls-reviewer` coverage; (b) the `wrr_advance_notices` table is now written into `01-core-data-model` design.md §6 as an explicitly flagged schema amendment to an already-`Approved` spec — BLOCKED pending its own dedicated `db-migration-verifier` pass (it does not inherit `01`'s existing verification); (c) the confirmed matching flow is now written into `07-incoming-receiving` requirements.md R1a / design.md §5.5 — BLOCKED pending `07`'s normal approval/sign-off process completing for this addition; and (d) 1D/linear barcode decoding for this flow is now written into `18-barcode-integration` requirements.md FR-2.3 — BLOCKED pending `18`'s normal approval/sign-off process completing for this addition. ## 5. Acceptance criteria

- [ ] A VMI party user with an unnarrowed or `vmi`-flow assignment sees their own live inventory position (occupied CBM / lot balances) and no other party's data.
- [ ] A Trading party user with an unnarrowed or `trading`-flow assignment sees their own pick-list/order history with final document price only, no margin/cost fields, and no other party's data.
- [ ] A party user with multiple active `user_party_scopes` assignments (multi-party and/or multi-flow) is presented an explicit switcher, and every read re-scopes server-side to the selected assignment.
- [ ] Supplies-flow data is never rendered or queried for a party user under any tested scenario, including a null-`flow_type` assignment on a party that is also a Supplies vendor.
- [ ] A party user can open their own `pick_list`/`acknowledgement_receipt` documents via a short-lived signed URL that re-authorizes on every access; the VMI disclaimer text is preserved verbatim.
- [ ] A party user cannot infer another party's records, documents, or notifications through IDs, counts, filters, errors, realtime events, or URL guessing.
- [ ] A party user's notification center shows only notices scoped to their current assigned party/flow, computed server-side.
- [ ] No mutation of inventory, pricing, billing, master data, or another user's access is reachable from this portal.
- [ ] A party user sees a scoped analytics view (VMI: occupied CBM trend, stock-on-hand, lot activity; Trading: order activity trend, item movement velocity) sourced entirely from `16`'s reusable components/party-scoped queries, with no margin/cost fields and no other party's or Supplies-flow data ever present — once `02`'s own approval/sign-off process for `reporting.read` (`assigned_party`) (added `02` design.md §3.2/§7.4, 2026-08-06) completes.
- [ ] A VMI party user can open their own `vmi_billing_statement`/`vmi_credit_notes` PDF artifact only (no structured native line-item rendering in v1), via the same signed-URL mechanism as `pick_list`/`acknowledgement_receipt` documents — once `02`'s own approval/sign-off process for `vmi_statements.read` (`assigned_party`) (added `02` design.md §3.2/§7.4, 2026-08-06) completes.
- [ ] Offline mode presents no cached/stale portal data as current, and no portal action enters the Tier 1 offline queue.
- [ ] An inbound-supplying (VMI vendor, or Trading `vendor`/`supplier`) party user can submit the thin barcode-label form (item limited to `party_visible_items`-reachable items, non-authoritative quantity, optional supplier lot number), generating a UUID-pointer 1D barcode label against a new `wrr_advance_notices` record; a Trading `customer`/`end_customer` never sees this surface; back office can confirm/convert the advance notice into a staged `wrr_items` line; and a floor scan at receipt matches the code to that line without bypassing `07`'s scanned-vs-expected discrepancy handling or WRR-creation ownership — once R11's four blocking items' owning specs complete their own approval/verification processes.
- [ ] Required Unit, integration, E2E, and manual checks in `tasks.md` pass before approval.
